// 无障碍功能

为所有人打造

GitFocus 专为辅助技术而设计。无障碍功能声明在每次发布时都会通过自动化测试和人工设备检查清单重新检查。

// 功能

支持的无障碍功能

🗣️
VoiceOver
支持

关键发布路径使用描述性标签、特征和逻辑阅读顺序。发布门记录了测试的路径和设备。

🔈
语音控制
支持

交互控件使用可访问的名称。物理设备检查清单验证了使用语音控制的关键发布流程。

🔡
更大文本
支持

应用程序文本使用 Dynamic Type。在批准此声明之前，需要自动化 AX3 和 AX5 覆盖以及人工 200% 文本大小检查。

🌑
深色界面
支持

应用程序支持浅色和深色外观。两者都包含在屏幕截图和应用程序无障碍功能发布检查中。

🎨
区分而不依赖颜色
支持

发布审查检查重要状态是否使用标签、形状或图标以及颜色。

◐
充足对比度
支持

自动对比度检查标记浅色和深色模式下的候选失败；审查员在批准前验证实际文本、图标和背景。

⏸️
减少动态效果
支持

发布检查清单验证重要动作是否尊重减少动态效果偏好或具有静态替代方案。

⌨️
完全键盘访问
支持

支持的流程包括键盘可访问的控件和重要仅手势操作的替代方案。

// 方法论

我们如何测试

  • 1

    iOS 原生审计 — Apple 内置的 performAccessibilityAudit API checks declared release routes for missing labels, undersized touch targets, and Dynamic Type issues.

  • 2

    极端大小渲染 — 每个屏幕在无障碍功能文本大小 AX3 和 AX5 下启动，以验证没有崩溃、不可读的截断或变得无法访问的情况。

  • 3

    阅读顺序验证 — 自动化测试验证 VoiceOver 在关键屏幕上按逻辑从上到下的顺序遍历元素。

  • 4

    对比度验证 — WCAG 对比度证据从渲染器拥有的语义区域生成，然后对照实际的浅色和深色图稿进行审查。

  • 5

    发布集成 — 无障碍功能套件在屏幕截图或元数据上传之前运行，并保留机器可读的证据。

我们遵循的标准

  • 文本和交互元素的 WCAG 2.1 AA 级对比度目标
  • Apple 人机界面指南的无障碍功能
  • 交互控件的最小 44pt 触摸目标检查
  • 无障碍功能文本大小下的语义 Dynamic Type 覆盖
  • 每个交互元素上的 VoiceOver 兼容标签和特征
  • 所有基于手势的交互的键盘可访问替代方案
